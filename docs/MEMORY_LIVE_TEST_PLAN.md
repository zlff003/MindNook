# Memory 真实模型长对话测试方案

制定时间：2026-10-14，真实 API 测试执行前。

## 测试目标

使用当前 `.env` 配置的百炼兼容 API 和 qwen-plus，实际执行 MemoryService 的摘要、提取、更正，再让真实模型根据实际注入的 MemoryContext 回答核验问题。评估长对话后的事实保持和错误，而非只验证程序不报错。

## 隔离与调用范围

- 全部对话为人工编写的虚构材料；不读取业务聊天记录。
- 独立 SQLite、独立 Chroma 集合和目录，保存于 `tmp/memory-live/<run-id>/`；Redis 用内存替身。
- 使用当前 FastEmbed 配置，实际建立向量索引。禁止静默切换 hash 或 Mock；无法初始化则报告阻塞。
- 保持当前摘要提示词、6000 历史预算、5000 批预算、400 字摘要、2048 输出上限、召回阈值和 top-k。配置实际值记录进报告。
- 60 轮主对话（120 条消息）：学生和助手历史均为预设材料；摘要、提取、更正、8 个核验回答真实调用 API。核验回答不写回历史，避免污染后续评分。
- 单次脚本最多 60 次逻辑模型调用；保留当前 API 超时和重试设置。达到上限则停止并报告，不无限重试。
- 本次走 MemoryService + RuntimeInput 的真实提示词组装，核验回复使用项目 RESPONSE_SYSTEM_PROMPT；不声称覆盖 Web/API 聊天路由、风险评估、完整 Agent 编排或生产 Redis/MySQL。

## 对话与验收点（运行前固定）

| ID | 输入情节 / 查询 | 期望 |
|---|---|---|
| L01 | 考试担忧导致凌晨约两点入睡，喜欢逐条讨论；助手仅建议呼吸练习 | 压缩后保留困扰与稳定偏好，不能将建议记成已尝试或有效 |
| L02 | 用户先说睡前列三项待办连续三晚有帮助，后来一周忙碌后无帮助 | 保留前后时间变化，不能继续无条件描述为有效 |
| L03 | 用户明确更正：之前说错，列待办实际没试过，记录是同学的 | 旧执行/有效事实失效；以后再问时不能当本人经历 |
| L04 | 转到宿舍夜间语音冲突，再转到课程小组分工 | 新话题进入摘要，旧未解决问题被保留而非默认解决；多次压缩边界单调且来源有效 |
| L05 | 原话“散步”，查询“去操场走一圈” | 实际 FastEmbed 召回能把改写查询关联到相应经历，并保留当前效果 |
| L06 | 长对话末尾和新会话询问睡眠/方法/回复偏好 | 来自旧原文的事实可通过摘要或长期记忆使用；特别检查来源已离开近期窗口 |
| L07 | 另一个学生相似的睡眠话题，独有标记“紫色风筝” | 原学生召回和回答不出现另一学生的独有内容 |
| L08 | 一个独立短会话只有两轮，下一会话询问内容 | 不靠摘要压缩，也能提取和召回有价值信息 |

## 证据和判定方法

1. 每轮记录摘要、边界、近期消息 ID、召回正文及来源、降级原因、SQL 记忆与版本。
2. 每次真实模型调用记录 purpose、发送的 messages、原始输出、服务端 model/usage、耗时和 request_id；不记录密钥或认证头。
3. 自动检查：摘要字数、边界单调、来源归属、压缩来源是否连续、当前输入不重复、索引同步和学生隔离。失败不掩盖。
4. 人工对照预设事实逐个阅读八个回答和其实际上下文，判定通过/部分通过/失败。模型没有得到的事实与模型收到却答错分开定位；不把关键词命中率当语义准确率。
5. 原始 JSON/JSONL/SQLite 留在测试目录；总结和真实输出摘录写入 `docs/MEMORY_LIVE_TEST_RESULTS.md`。脚本放在 `scripts/memory_live_eval.py`，必须显式 `--live` 才调用 API，不纳入普通 pytest。
6. 先评估当前代码基线。本轮不为使测试通过而修改业务提示词、预算或逻辑；发现问题明确报告。

## 执行中补充的诊断（不覆盖基线结果）

- 第 36 轮 P3 的真实回答包含表情符号，Windows GBK 控制台打印失败。只修复测试脚本日志编码并增加断点续跑，从第 37 轮继续；保留之前的调用和失败记录。
- P4 的多问题核验被模型按“一次一问”的偏好只回答了一部分。因此增加最多两次单问题对照：使用已保存的 P4/P6 实际上下文，仅替换最终问题，检查早期入睡时间和列待办更正。该对照不重新检索，不把它当成新的完整端到端测试，也不把已知正确答案提供给模型。额外调用单独记账。
- 如果主运行的 60 次调用上限阻止 P8 短会话测试，则在同一个隔离测试库中补完该项，最多再调用一次提取、一次回答；与前述对照合计最多 4 次附加逻辑调用。主运行的预算触发记录保留，不把它算成产品 API 失败。
