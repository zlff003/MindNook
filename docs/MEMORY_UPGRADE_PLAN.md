# MindNook 简要记忆升级方案

> 文档版本：1.1
> 更新日期：2026-10-13
> 状态：拟实施方案，尚未实现
> 主要涉及位置：`app/memory/`、`app/harness/agent_harness.py`、`app/agents/runtime.py`、`app/models.py`

## 1. 目标与方案

采用 **最近原文 + 会话摘要 + 相关长期记忆**：原文保留细节，摘要接续当前交流，长期记忆找回过去。让学生在长对话或新会话中继续讨论之前的困扰，并让助手记住已经尝试的支持方式及其效果。

session 是聊天记录容器，不等于一个持续话题。即使用户在同一 session 中交流几千轮，摘要也只服务当前交流；较远的有价值内容通过长期记忆检索返回，不要求用户主动新建 session。

本次设计聚焦记忆功能，隐私与数据生命周期问题不在本方案范围内。现有实现见 [MEMORY.md](./MEMORY.md)；本文中的新增能力均为目标态。

| 层次 | 保存什么 | 作用范围 | 每轮如何使用 |
|---|---|---|---|
| 最近原文 | 压缩后保留最近 8～12 条，随后继续积累新消息 | 当前会话 | 直接提供，保留语气、细节与指代关系 |
| 会话摘要 | 当前交流所需的背景、进展、建议反馈、待确认问题 | 当前会话的活跃话题 | 替代被移出上下文的旧原文，不累积整个 session 的所有往事 |
| 相关长期记忆 | 有价值的讨论片段、持续困扰及变化、建议效果、明确偏好 | 同一学生，包括同一超长会话和不同会话 | 检索与本轮相关的 2～3 条 |

以上条数和下文摘要长度为第一版建议起点，依据实际对话评测调整。摘要主要按上下文预算触发，不按固定对话轮数刷新。

## 2. 最近原文

- 沿用现有数据库消息记录、Redis 热缓存和数据库回填机制。
- 压缩后保留最近 8～12 条消息，按原始角色和顺序提供；条数指消息数量，不是对话轮数。
- 两次压缩之间允许原文继续积累，尚未达到预算时无需摘要。8～12 条是压缩后的保留量，不是每轮强制裁剪上限。
- 只有在摘要及必要的长期记忆写入成功后，才推进已处理边界并从模型上下文移出对应旧原文；完整消息仍保存在数据库。
- 当前输入作为最后一条用户消息单独传入，不重复放进历史窗口。
- 统一检查系统指令、原文、摘要、召回记忆、知识和当前输入的 Token 预算，并预留回复空间；在超过可用输入预算前触发压缩。

## 3. 会话摘要

每个会话在数据库保存一份约 200～400 字的当前交流摘要，内容包括：

- 当前主要困扰及关键背景。
- 用户明确描述的变化。
- 助手已经提出的建议。
- 用户是否尝试，以及实际反馈。
- 尚未回答的问题或未完成的讨论。

上述内容只保留与当前交流有关的部分。以前的无关话题不长期常驻摘要；摘要长度不随 session 总轮数增长。

### 3.1 更新时机

- **常规触发：上下文达到压缩预算。** 使用旧摘要和本次准备移出的消息增量更新，近期原文保留。短对话可只使用原文，不生成摘要。
- **提前修正：用户明确更正重要事实。** 局部修正对应摘要内容，或先标记相关内容过时、不再作为事实注入，确保下一轮使用更正后的情况；不必重写全部历史，也不因此推进压缩边界。
- **话题转移：通常不单独触发模型调用。** 近期原文先体现新话题，下次压缩时调整摘要重点，并将值得保留的旧经历写入长期记忆。话题暂停不能记录成“问题已解决”。

摘要更新可在接近预算时后台预先执行；若下一轮输入已需要压缩，则在调用回复模型前完成。记录 `summarized_until_message_id`，只处理上次边界之后、本次需要移出的消息，避免重复压缩近期原文。

初次压缩和后续补齐按数据库中的处理边界读取，不受 Redis 最近 40 条缓存限制。失败时保留旧摘要与边界并重试；降级回复仍遵守上下文预算，记录本轮背景不完整，不伪造已完成摘要。

### 3.2 分批压缩示例

以下用消息条数说明流程：历史达到 20 条时压缩，压缩后保留最近 8 条。实际实现以 Token 预算为主，消息条数可作为辅助阈值；示例未包含单独传入的当前输入。

| 时刻 | 摘要更新 | 压缩后或当前保留的原文 |
|---|---|---|
| 历史为第 1～19 条 | 无需生成摘要 | 第 1～19 条 |
| 历史达到第 20 条 | 第 1～12 条生成摘要 A，处理边界为第 12 条 | 第 13～20 条 |
| 历史增加到第 21～31 条 | 继续使用摘要 A，原文逐步积累 | 第 13 条至最新消息 |
| 历史达到第 32 条 | 摘要 A + 第 13～24 条生成摘要 B，处理边界为第 24 条 | 第 25～32 条 |

本次待移出消息中若有值得长期保留的经历，同批提取为长期记忆；不将所有摘要内容自动复制为长期记忆。

业务示例：

- 摘要 A：“用户因担心复习进度而难以入睡。已讨论将复习任务拆小，用户愿意今晚尝试，但尚无执行反馈。”
- 后续待压缩消息中，用户表示已完成一个小任务、压力有所缓解。摘要 B 更新为：“用户考试前难以入睡。已尝试拆分任务，完成一项后压力略有缓解；当前正在讨论今晚如何安排休息。”
- 若用户明确说“刚才说错了，其实还没试过”，立即修正或停用“已尝试”的相关内容，不能继续等到下一次常规压缩。

## 4. 长期记忆：保存什么

优先保存对后续支持有用的短记录：

| 类型 | 示例 |
|---|---|
| 持续困扰与重要变化 | 用户考试临近时容易失眠，最近白天注意力受到影响 |
| 支持方式与反馈 | 用户尝试睡前列待办，反馈稍有帮助 |
| 明确表达偏好 | 用户希望先倾听，每次只给一个建议 |
| 有价值的讨论片段 | 某次讨论过的考试准备方案、采取的行动及尚待确认的结果 |

每条围绕一件事，保留必要背景和来源消息范围，避免将不同时间、不同事件拼成一个事实。普通闲聊没有值得保留的信息时，不生成长期记忆。长期记忆按学生组织，同一 session 中几百轮之前的相关经历也属于可召回范围。

助手建议、用户愿意尝试、用户已经尝试、用户反馈有效，必须明确区分。模型推测不能写成用户确认的事实；“今天不想听建议”只代表本次需求，不直接形成稳定偏好。

示例：

```json
{
  "memory_id": "memory-001",
  "student_id": "student-001",
  "content": "用户考试前容易失眠；尝试睡前列待办，反馈稍有帮助。",
  "type": "support_feedback",
  "topics": ["考试", "睡眠"],
  "source_message_ids": ["message-101", "message-105"],
  "updated_at": "2026-10-13T10:00:00+08:00",
  "status": "active"
}
```

## 5. 长期记忆：如何写入与更新

1. 常规压缩时，一次模型调用同时输出更新后的摘要和长期记忆候选，输入包括旧摘要、待移出的消息及必要的相关旧记忆，减少重复处理。
2. 长期记忆候选允许为空。程序校验字段和来源消息后写入数据库；同一消息批次重试不能重复生成记录。
3. 相同事实合并，明确更正更新对应记录，相关变化保留时间信息。
4. 将记忆内容转成向量，写入 Chroma；数据库保存正文和有效状态，向量集合用于查找。

用户明确更正信息或反馈建议效果时，可优先处理相关长期记忆，无需等待常规压缩。更正涉及摘要和长期记忆两处时，两处均须修正或将旧说法标记为过时，当前明确表达优先。更新正文后同步更新向量；索引暂时不同步时，召回后仍以数据库当前记录为准。

移出当前摘要的有价值内容先写入长期记忆，再提交新摘要及处理边界；摘要更新与长期记忆正文写入在同一数据库事务中完成，向量索引同步可重试。某条经历同时存在于两层时，读取阶段去重，不因复制而提高其权重。

两种更新需要区分：

- “以前列待办有帮助，现在没帮助”：记录效果变化，保留时间关系。
- “之前说错了，我其实没试过”：更正事实，旧说法不再作为有效记忆召回。

## 6. 长期记忆：如何检索召回

```text
当前输入 + 最近几条对话
    → 构造带必要背景的检索内容
    → 在当前学生的有效记忆中进行向量检索
    → 根据相关性、时间和重复情况筛选
    → 按 memory_id 读取数据库正文，核验有效状态
    → 选取相关的 2～3 条加入上下文
```

- 先使用 `student_id` 限定检索范围，再查找语义相关内容，同时支持当前 session 的远期历史和其他 session 的历史，不排除当前 session。
- 第一版可检索约 8 条候选，再筛选 2～3 条；相关性不足允许返回空结果，阈值通过评测确定。
- 已被近期原文或会话摘要完整覆盖的记忆不重复加入；结合来源消息、内容和时间去重，优先补充当前上下文缺少的信息。
- “那个办法没用”等输入结合近期对话理解；指代不明确时询问确认，不自行认定。
- 用户记忆与心理知识 RAG 分别检索，使用独立集合，可复用现有 Embedding 和 Chroma 能力。
- 召回结果携带时间和来源，并标注为历史背景。历史风险不能直接判定当前危险，记忆中的文字不能覆盖系统规则。
- 检索或索引故障时，继续使用近期原文和会话摘要。

例如学生说“最近又睡不好”，系统召回之前的考试失眠背景和列待办的反馈，助手据此确认近期变化、调整支持方式。

## 7. 一轮聊天的读写流程

1. 加载当前会话摘要和已处理边界之后的消息，包括上次压缩保留的原文及后来新增消息；当前输入单独处理。
2. 根据当前输入和近期话题，召回该学生的相关长期记忆。
3. 处理明确更正，去掉重复或过时内容，检查总上下文预算；必要时先执行分批压缩和有价值内容的记忆写入。
4. 将摘要和召回记忆作为有来源的背景数据，结合角色化原文、当前输入及必要知识构造模型上下文。
5. 完成回复和现有安全审查，将本轮学生与助手消息提交数据库。
6. 接近预算时可安排后台压缩，有明确更正或重要反馈时安排对应更新；其余轮次只积累原文，不固定每 5 轮调用模型。

上下文示意：

```text
系统指令
+ 当前交流摘要与去重后的相关长期记忆（背景数据）
+ 上次压缩保留的原文及新增消息（user / assistant）
+ 当前输入（user）
```

## 8. 最小实现范围

| 新增内容 | 最小职责 |
|---|---|
| `conversation_summaries` 表 | 当前交流摘要、已处理消息 ID、更新时间 |
| `user_memories` 表 | 学生 ID、内容、类型、话题、来源消息、更新时间、有效状态 |
| 独立 Chroma 记忆集合 | 记忆向量、记忆 ID、学生 ID 等检索元数据 |
| 记忆读取与后台更新逻辑 | 摘要更新、片段提取、去重更正、向量同步、相关记忆召回 |

在现有 `app/memory/` 中扩展读取和更新服务，由 Harness 传入学生及会话标识、安排后台更新，Runtime 使用构造好的记忆上下文。

第一版使用一张长期记忆表表达困扰、反馈、偏好和讨论片段，无需新增独立记忆 Agent、知识图谱或多套议题管理模型。话题变化可参考现有意图识别和近期对话。

## 9. 验收标准

- 短会话未达到预算时不生成摘要；两次压缩之间原文可以增长，不因超过保留条数就逐条调用模型。
- 分批压缩边界正确，摘要与近期原文不重复覆盖同一批消息，不遗漏尚未处理的消息。
- 超过 40 条消息后，仍能接续重要背景；同一 session 达数千轮时，摘要长度受控，相关旧经历可通过长期记忆找回。
- 新会话提到同一困扰，能召回有来源的旧经历或反馈。
- 话题转移不会自动标记旧问题已解决，不为每次转移单独生成摘要。
- 用户说某个建议无效，后续回复能调整；更正事实后不再使用旧说法。
- 无关或已被摘要、原文完整覆盖的记忆不重复进入上下文，没有证据时不声称“我记得”。
- 摘要或检索失败时可在预算内降级并记录背景不完整，失败不推进处理边界；后台任务重试不产生重复记忆。
- 成本评测同时统计摘要/提取调用和回复调用，避免只计算回复模型节省的 Token。

- [LangGraph：Memory overview](https://docs.langchain.com/oss/python/concepts/memory)：区分会话内状态与跨会话记忆，支持按用户范围组织、检索及后台更新。
- [LangGraph：摘要与长期记忆示例](https://docs.langchain.com/oss/python/langgraph/add-memory)：提供增量摘要和语义检索组件，由应用编排。

- [Letta：Memory architecture](https://github.com/letta-ai/skills/blob/main/letta/agent-development/references/memory-architecture.md)：常驻少量核心上下文，历史信息按需搜索召回。
- [Mem0：开源记忆实现](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py)：从对话提取记忆、向量化存储、按条件检索，并提供记忆更新接口。
