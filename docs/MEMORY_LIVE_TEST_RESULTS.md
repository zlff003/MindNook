# Memory 真实模型长对话测试结果

日期：2026-10-14。运行：`baseline-20261014`。

**结论：当前版本没有通过长对话效果验收。** 短会话跨会话提取、近期原文中的事实回顾、部分更正和用户隔离可用；持续压缩、事实与来源的语义一致性、更正范围、长距离及跨会话事实保持存在明确缺陷。此前 Mock 测试通过不能代表这些能力可靠。

## 实际执行内容

- 模型：现有 `.env` 的百炼兼容 API，实际返回 `qwen-plus`。没有用 Mock 生成摘要、提取、更正或核验回答。
- 主场景：60 轮、120 条消息；另外有另一学生的一轮对话和独立学生的两轮短会话。
- 对话材料是固定的虚构学生与助手文本。真正调用模型的是 Memory 处理与核验回答，不是让两个模型自由对聊。
- 核验覆盖：考试睡眠 → 方法效果变化 → 明确更正 → 宿舍沟通 → 课程小组 → 同会话远期回顾 → 新会话回忆 → 用户隔离 → 短会话召回。
- 使用真实临时 SQLite、真实 FastEmbed `BAAI/bge-small-zh-v1.5`（512 维）、独立持久化 Chroma；Redis 使用内存替身。
- MemoryService、SummaryGenerator、SQL 存储和校验、RuntimeInput 提示词组装均为当前项目代码。核验回答使用项目的 RESPONSE_SYSTEM_PROMPT；没有执行完整聊天路由、风险审查或所有 Agent。
- 保持原配置：历史预算 6000、批预算 5000、摘要上限 400 字、Memory 输出上限 2048、召回阈值 0.45、top-k 3、API 超时 20 秒、最多重试 1 次。
- 本轮只新增测试脚本和文档，未修改业务逻辑、业务数据库、业务向量集合或 `.env`。

## 关键原始例子

### 1. 起初说得很明确，后面却声称没提供过

第 1 轮原文：

> 我最近为三周后的统计学考试担心……通常拖到凌晨两点才睡，早上八点还得上课。

P4 单问题对照：

> 我们最初聊睡眠时，我说自己通常几点才能入睡？只回答这一件事，没有确切记录就说明不知道。

真实回答：

> 你之前没有提供具体入睡时间，所以目前不知道。

原始消息仍完整保存在 SQL；问题发生在给模型准备的上下文中。最初这条消息已离开近期窗口，摘要和可召回记忆都没有保住对应事实。这也说明降级时不能把“当前上下文不知道”说成“用户从未提供”。

### 2. 引用了存在的消息 ID，却引用错了事实

第 2 次 API 调用是第一次摘要。批内第 1 条消息是“统计学考试、凌晨两点入睡”，本轮 focus 则是后来第 16 轮的“准备向助教问独立事件题”。

模型把“计划在助教答疑时间提问”写成摘要和长期记忆，却引用了第 1 条消息的 ID `72cbdd53-2908-457d-b00c-d023a43aa99d`。该输出通过了现有校验并入库。

这不是伪造不存在的 ID，而是**存在的 ID 与事实不匹配**；只核对来源 ID 是否允许、是否属于当前学生，不能防住这种错误。虽然提示词禁止把 focus 中未入批的事实提前写入，真实模型没有遵守。

### 3. 更正列待办，误撤回了散步

第 25 轮原文明确说：

> 之前说错了，列待办其实没试过……记录都是同学的……散步是我自己做过的。

第 11 次调用先撤回了清单记录。紧接着第 12 次摘要调用却生成：

```json
{
  "action": "retract",
  "memory_id": "a38027b3-3bf9-4c31-b179-d3143162fd66",
  "content": "学生连续四天坚持晚饭后操场外圈散步，主观感受为身体紧绷缓解、思绪变慢；但观察到入睡时间仍波动，故未将散步视为失眠解决方案。",
  "source_message_ids": ["7d0f6b85-7209-4f31-a2de-9f1f12ef81cf"],
  "change": "correction"
}
```

SQL 接受了这条操作，散步记录变为 `retracted`，原证据被标记失效。这直接违背了用户本次明确表达。

同次输出还要求新增正确的“本人从未尝试过列待办”记录，但未保存下来：前一次撤回记录已把最新更正消息加入 evidence，下一次提交把整条已撤回记录的全部来源视为 retired，导致**最新的更正证据也被一起屏蔽**；新更正记录被跳过，对应摘要也被标记 disputed。

### 4. 长历史反复处理，却无法前进

离线按每次真实输入重放校验，收到输出但失败的 23 次中：

- 20 次：`old summary evidence would be silently discarded`。
- 1 次：`invented or unauthorized source message`。
- 2 次：`invalidated evidence cannot become an active fact again`。

旧摘要包含后面轮次的变化，但后续压缩继续处理较早批次；模型反复生成遗漏旧摘要来源的结果，当前策略是整批拒绝、下轮再调用，缺乏有效的修复或收敛路径。边界停在第 24 条，预算内只留下后面的原文，中间大量历史没有进入当轮模型上下文。

### 5. 模糊提及更正，会扩大停用范围

第 58 轮只是提醒“前面已经更正过的清单记录……以我明确说明的实际经历为准”，没有新增明确的事实替换。关键词仍触发更正流程；API ReadTimeout 后，quarantine 分支将关联的助教经历与交流偏好也标为 disputed，召回一度变空。第 60 轮又恢复了偏好，但助教记录仍 disputed。

这表明更正候选匹配和失败暂时停用范围偏宽，可能影响并未被用户否定的其他信息。

## 需要优先修复的方向

1. **事实与来源对齐**：限制 focus 的用途；对新增事实和撤回操作增加语义证据检查，不能只验证 ID 存在。
2. **纠错作用范围**：撤回目标必须确实与用户更正冲突；只让旧错误证据失效，不能把最新更正证据及同一消息中的其他正确事实一并封禁。
3. **摘要失败收敛**：区分旧摘要与当前批次的时间关系；对漏项进行有限修复或保守合并，避免持续重复整批失败；显式监测边界长期停滞。
4. **超时与重试**：当前 20 秒读超时对本次结构化输出不稳定，应单独评估 Memory 超时/输出量/重试预算，而不是每轮重复消耗约 40 秒。
5. **记忆注入后的回答**：区分“一次只问用户一个问题”和“只回答用户一个问题”；缺少历史时说明当前没有记录，而不是断言用户从未说过。

本轮未修改这些业务逻辑，应修复后使用同一素材重新运行，保留当前基线作对照。

```powershell

python scripts/memory_live_inspect.py <运行名>
python scripts/memory_live_controls.py <运行名> --live
```

主运行曾因 Windows 控制台无法编码模型返回的表情符号，在第 36 轮 P3 记录完成后中断。只修复了测试日志编码并从第 37 轮继续；没有重新请求此前结果。日志编码问题与产品 Memory 缺陷分开记录。主脚本最后退出 0 只表示场景执行结束，不表示语义验收通过。

新增脚本已通过 Python 语法检查；`git diff --check` 通过，仅有现有文件的 LF/CRLF 提示。本轮没有修改业务代码，因此没有重复此前 132 项离线回归，也没有把旧结果计入本轮。

本次只是一个固定长对话样本及少量对照，不是大规模统计评测。但来源错引、错误撤回、边界长期停滞和跨会话遗忘均有具体输入输出与数据库证据，已足以说明当前长对话 Memory 尚不可靠。
